NCMA Metro Maryland Chapter Admin panel specification
Developer specification

Content admin panel

A custom authoring interface on ncmametromd.org that lets chapter officers publish and maintain site content without touching code. Built into the existing Next.js application, backed by the project’s own database.

1. Scope

Six content types are managed through the panel. Every public page that currently holds hand-edited copy reads from the database instead.

Insights articles
Title, standfirst, body, author (linked to a board member), category, read time, hero image, publish date, featured flag.
Newsletter issues
Issue number, date, subject line, body, linked articles, send status. Archive page renders past issues.
Board bios & headshots
Name, board position, organization, sector label, email, LinkedIn URL, bio, headshot, display order, body (Directors or Advisors), active flag.
Events
Title, date and time, location, description, registration URL, image. Coexists with the Eventbrite feed — see §7.
Sponsors
Organization name, tier, logo, website URL, display order, active flag.
Homepage copy
Named text blocks (hero headline, chapter description, membership pitch, calendar note) editable in place. No structural layout changes from the panel.

2. Roles and access

Access is limited to a small set of chapter officers. Two roles, assigned per user.

Editor
Creates and edits any content type. Can save drafts and submit for review. Cannot publish, delete, or manage users.
Administrator
Everything an Editor can do, plus publish, unpublish, delete, reorder rosters, and invite or remove panel users. Expected holders: President, VP Communications.

3. Publishing workflow

Every item carries a status: Draft, In review, Published, or Archived. Role determines what a save can do.

  • An Editor saving a finished item moves it to In review and notifies administrators by email.
  • An Administrator can publish directly from any state, skipping review.
  • Published items remain editable; edits create a new draft revision that does not affect the live page until published again.
  • Unpublishing returns an item to Archived and removes it from the public site without deleting it.
  • Every save records author, timestamp, and a restorable revision.

4. Editor requirements

Article and newsletter bodies need full layout control. The editor stores structured content (a block model, not raw HTML) so the public site can render it in the chapter’s type styles rather than inheriting pasted formatting.

  • Headings (two levels), paragraphs, ordered and unordered lists, bold, italic, links.
  • Pull quotes as a distinct block, with optional attribution.
  • Images as a block with caption and alt text; drag to upload, drag to reposition within the flow.
  • Full-width and inset image variants.
  • Paste from Word and Google Docs strips foreign styling and maps to the block model.
  • Live preview that renders the article exactly as the public page will.
  • Autosave every few seconds with an explicit last-saved indicator.

5. Screens

Sign in
Email and password, or a magic link. No public registration — accounts are created by invitation only.
Dashboard
Items awaiting review, recent drafts, upcoming events, and a count of board members with missing bios or headshots.
Content lists
One per content type: searchable table with status, author, last edited. Bulk publish and archive. Drag to reorder where order matters (board roster, sponsors).
Item editor
Fields on the left, live preview on the right. Status control, revision history, and publish actions in a persistent header.
Media library
Uploaded images with alt text, searchable and reusable across content types.
Users
Administrator only. Invite by email, assign role, revoke access.

6. Technical notes

  • Built into the existing Next.js application at /admin, deployed with the site on Vercel.
  • Database: Postgres (Vercel Postgres or Supabase). Content tables plus a revisions table keyed by item and version.
  • Authentication: session-based, with all /admin routes and mutation endpoints protected server-side. Role checked on the server, never only in the UI.
  • Image uploads to blob storage with automatic resizing; headshots normalized to a 4:5 crop to match the current roster layout.
  • Public pages read published content at request time or through incremental revalidation, so a publish appears within seconds without a redeploy.
  • Seed the database from the current site content as part of the initial migration — the thirteen directors, ten advisors, and existing bios already exist in the redesign files.

7. Supabase setup

The backing service is Supabase: Postgres, authentication, and file storage in one project. A companion document, Supabase schema, carries the SQL to create every table, trigger, and security policy described here.

  • Project. One Supabase project per environment — production, and a staging project for testing migrations before they touch live content.
  • Authentication. Supabase Auth with email magic links. Public sign-up disabled; officers are invited from the dashboard or the panel’s Users screen. A profiles table extends auth.users with the Editor or Administrator role.
  • Authorization. Row-level security on every table, so permissions hold even if a request bypasses the interface. Anonymous visitors read only rows with status published; staff read all rows; publishing and deletion require the administrator role.
  • Storage. Three public buckets — headshots, media, logos — with uploads restricted to signed-in staff. Headshots are resized and cropped to 4:5 on upload to match the roster layout.
  • Next.js integration. Use @supabase/ssr so sessions work in server components and middleware. Public pages query with the anon key and rely on RLS; the admin panel uses the signed-in user’s session. Never expose the service-role key to the browser.
  • Environment variables. NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY in Vercel for both preview and production; SUPABASE_SERVICE_ROLE_KEY server-side only, for admin operations such as inviting users.
  • Publishing freshness. Public pages revalidate on a short interval or on demand via a webhook from Supabase, so a publish appears within seconds without a redeploy.
  • Migrations. Keep schema changes in the repo under supabase/migrations and apply them through the Supabase CLI, not by hand in the dashboard.

8. Open questions

  • Events and Eventbrite. The repo already pulls events from the Eventbrite API. Decide whether the panel replaces that feed, supplements it with chapter-only listings, or edits presentation while Eventbrite remains the source of record.
  • Newsletter delivery. The panel authors and archives issues but does not send email. Confirm the sending platform (Mailchimp, Constant Contact, Resend) and whether the panel should push an issue to it or export for manual send.
  • Board member self-service. Current scope limits access to officers. If board members should edit their own bios later, plan the role now — it is cheaper than retrofitting.
  • Approval notifications. Confirm whether review requests go to a shared chapter address or to individual administrators.
